# 故障查询与恢复 API（v3.5 SDK 补充）

适用：配套 v3.5 下位机的 Python SDK。此次只更新 SDK 与文档，不修改固件，不需要因本补充重新刷写。

跟随误差故障后的参数起点及提速条件见[日常运动参数建议](日常运动参数建议.md)：首次/故障后建议显式使用0.5°/s、1°/s²，保持误差阈值0.75°，排除原因后再逐项提高。

## 接入方式

```python
from app import MotorError, explain_error, get_fault_advice
from dataclasses import asdict

# controller 为已连接的 MotorController
report = controller.get_fault_report()
print("诊断是否完整:", report.complete)
for issue in report.issues:
    print(asdict(issue))  # domain/code/title/motor_id/detail/steps/apis/execution_unknown

# 捕获任何一次 API 调用错误，提供可展示给操作员的处理步骤。
try:
    angle = controller.get_current_angle(1)
except (MotorError, ValueError) as exc:
    advice = explain_error(exc)  # 不访问串口，不执行恢复
    print(advice.title, advice.detail, advice.steps, advice.apis)

# 已知代码也可离线查询；必须指定命名空间，不能只传数字7。
tracking = get_fault_advice("trajectory", 7)
```

`MotorError` 及其子类也有 `exc.recovery` 属性；`ValueError` 使用 `explain_error()`。
`apis` 是可调用方法名的提示，不是自动执行列表；每个接口都有前置条件。
`execution_unknown=True` 表示运动执行结果可能未知，不允许自动重发。

`get_fault_report()` 查询轨迹和两轴位置里的报警/保护，返回顺序采样快照；不发送停止、复位、运动或标定命令。读取失败仍返回已读到的结果和错误建议。`complete=False` 表示读取不完整或角度不可信，禁止把空列表当作健康。即使 `complete=True` 且没有故障，也不代表已停稳、已在首点或允许启动。读取反馈可能使固件撤销不可信的参考，这是现有反馈保护行为。运动期间低频按需查询，避免总线负载；诊断不是同步采样的运动控制接口。

## 三个清除入口

| API | 用途 | 不会做的动作 |
| --- | --- | --- |
| `reset_alarm(motor_id)` | 停止该轴后尝试复位驱动报警，返回剩余报警码 | 不修复硬件、不复位编码器、不清轨迹 |
| `clear_guard_fault(motor_id)` | 确认该轴保护，保留原参考、限位输入映射、软范围、保护策略 | 不设零、不放宽保护、不启动动作 |
| `clear_trajectory_fault()` | 确认停稳及保护条件后丢弃旧轨迹会话，成功返回 IDLE | 不回起点、不清驱动报警、不自动继续 |

`clear_guard_fault()` 复用固件已有的原保护策略确认命令，并校验配置及参考原点读回。上传、预载或运行中的双轴任务、未停稳、参考失效、回零中、驱动报警、越界及配置的活动限位都会拒绝。清除后还会再次核查故障、限位、角度和驱动报警。参考失效时不提供强制清除，必须在已知真实姿态调用 `set_current_angle()` 或在正确传感器配置下重新回零。配置不会因清除被自动关闭。

清除不是解决根因。对于编码器、主电源、制动回路、继电器、IPM等问题，软件只能提供诊断与复位尝试；需要按说明书处理硬件。未知报警码有保守排查提示，不猜测其意义。

## 推荐恢复顺序

1. 保存故障码、实际角度、误差与周期。调用 `stop_trajectory()` 处理双轴任务；单轴任务使用 `stop(motor_id)`，确认实际停稳。通信失效且停不住时使用硬件急停。
2. 排除表中原因。驱动报警通过 `read_alarm()` 读取，必要时 `reset_alarm()`，确认返回0。通信结果未知时先安全停止，`close()` 后 `connect()`，禁止重发旧运动。
3. 读取 `get_axis_positions()` 和 `get_feedback()`。参考有效就保留；参考无效才在已知真实姿态重新标定或回零，不要把故障停止位置随意设为0。
4. 若单轴 `guard_fault` 非0且参考仍有效，显式调用 `clear_guard_fault(1)` / `clear_guard_fault(2)`。不要为清故障扩大范围、关闭限位或修改零点。
5. 若旧轨迹处于故障/取消/完成终态，调用 `clear_trajectory_fault()`。重新标定已使轨迹回到IDLE时该接口直接返回空闲；不需再次清除。
6. 重新核对真实位置和路径。需要回旧首点时先确认经过路径安全，再 `prepare_return_to_start(original_points)`；它只预载，仍需明确 `start_trajectory(session)`。回到首点后重新准备业务轨迹。不要自动续跑旧会话。

例如截图中的轨迹7、驱动报警0，如果两轴参考仍有效且单轴保护为0，处理跟不上原因并停稳后，只需 `clear_trajectory_fault()`。通常无需改机械零点。

## 无报警码但异常的情况

- SON一接就转：先断开SON并确认停止，检查PA4/PA14/PA22、PA24～PA27、PA53及CMODE实际输入。使用 `read_pa()` 查询；不自动保存启动参数或触发使能。本问题不能靠清轨迹故障解决，仍需现场核对冷启动配置。
- 停止确认超时：实际停止状态未知，使用硬件急停并检查速度源、模式、接线及制动，禁止只清软件状态。
- 回零失败：检查 `get_feedback()` 的 `home_phase` 和 `fault`，用上面的guard命名空间查询。回零超时/取消通常使参考失效。
- 当前角度未知或反馈过期：停止依赖角度的新运动，检查通信与参考，不能把None或过期值替换成0。
- SDK等待超时/会话变化/读回不一致：异常原文保留在advice.detail；读取真实状态确认，不能把命令接收等同于完成。
- 未列出的未来故障码：返回原始代码、版本核对和联系维护人员的步骤；不自动清除或重启。
