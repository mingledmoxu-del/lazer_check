# v3.8.7：起步平滑与板端停稳完成反馈

## 对本次现场时间的解释

用户确认这组测试已经是v3.8.6。截图中完整换点约2.3～2.7秒，其中运动约1秒，进入±0.5°后至停稳约0.66～1.19秒，再核验约0.18～0.24秒。固件实际结束容差约±0.037°（默认PA11=10000、50:1），所以“进入±0.5°→完成”包含物理收敛，不能都算作通信或软件等待。

目前没有原始逐帧日志和振动测量，不能确认机械振动来自起步冲击、制动、间隙或驱动整定；本次不改驱动器PA40、PA41、PA42，不承诺仅靠软件把约3秒压到某个固定值。

## 本次修改

- 起步分段限速，约200ms从零升至请求速度；只有加速受该限制，制动仍可立即降低指令，避免妨碍现有制动距离和限位保护。这不是完整的S曲线或硬实时速度规划。
- 进入到位容差后明确进入制动/停稳阶段，保持零指令、以20ms调度采集两次实际零速，停稳后仍超差才修正。不放宽原到位容差，不把单次四舍五入后的零速当作完成。
- 新增板端点位活动/完成标志，完成需实际位置在容差内、已发零速、两次独立实际零速；之后查询仍检查当前位置、报警、参考和保护。STOP、任务替换、通信或执行故障撤销完成证据。
- SDK等待可复用该完成证据，减少“板端确认完→SDK再等两次”的重复工作。
- 新增两轴直接反馈快照及组合等待API，减少分轴位置/速度/报警/最终核验的多轮TCP请求。

## 新接口

```python
poses = controller.get_axis_positions(fresh=True)
poses = controller.wait_for_axes((10, 5), tolerance_deg=0.1, timeout_s=120)
```

两轴快照0x37，parameter=0x4652（FR），空payload；数据格式与原0x37相同，source=0，速度/位置/报警来自直接驱动应答，单位元数据在有效期内复用。两轴按顺序读取，不是同步采样。原parameter=0继续允许新鲜缓存。旧固件不支持FR，会拒绝，需同步更新SDK与固件。

flags的0x20表示点位任务活动、0x40表示完成证据。已有参考/软保护/停机待确认位保持原定义。`point_active`/`point_completed`可从SDK反馈对象读取。`wait_for_axes()`不发运动：确认两轴位置、来源、采样年龄、实际零速、报警和保护；板端都已完成可直接返回，否则至少两轮直接停稳快照。超时或保护异常请求两轴停止，不重发运动。

同事的上层业务应把原来多次逐轴查询及最终核验改成组合等待；仅换固件而不改上层重复核验，无法消除上层自己的等待。默认组合容差0.1°，可按需求指定，但不改变板端定位容差。
