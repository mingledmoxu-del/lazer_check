# v3.4：轨迹加速度可配置、轨迹故障确认清除

日常调试以[日常运动参数建议](日常运动参数建议.md)为准：速度0.5～1.5°/s、加速度1～3°/s²，首次或故障后从0.5和1开始。下文关于加速度5的说明用于解释接口可配置，不代表推荐日常使用5。

本版继续使用115200/8N2驱动总线、115200/8N1 PC串口。加速度参数覆盖只需更新Python SDK；独立轨迹清故障命令需同时烧录v3.4固件，旧固件会明确拒绝，不会假装成功。没有自动使能SON、改保存的上电配置、放宽误差保护或重新置零。

## 两种“加速度”必须分开

| 层次 | 接口/参数 | 单位与作用 |
|---|---|---|
| 驱动器内部加减速 | PA40/PA41/PA42；`set_motion_profile` | 毫秒：驱动器加速、减速与S曲线时间，不是°/s² |
| 轨迹规划/速度更新限制 | `max_accel` | 输出轴°/s²：检查轨迹段间速度变化、运行时限制速度指令变化 |

驱动器参数通常在设备调试时确定，不需要每个轨迹点重写。轨迹加速度不能因此取消：若目标变化比驱动器/负载实际响应快，仍可能产生跟随误差。改变其中一层不会自动改变另一层。

`max_accel=5`表示5°/s²；`set_motion_profile(..., accel_ms=5)`表示5毫秒，是完全不同的设置。修改驱动器时间参数时先停稳，并用`get_motion_profile`读回，不能把这两个数值互相照搬。

## 日常API可以覆盖默认值

```python
ready = motors.prepare_business_trajectory(
    points,
    max_speed=0.5,     # 输出轴°/s；先从保守值验证
    max_accel=1,       # 输出轴°/s²，不写PA40/PA41
    max_error=0.75,
    tolerance=0.3,
    cycle_ms=100,
)
motors.start_trajectory(ready.session)
motors.wait_trajectory(ready.session)
```

无参数时仍使用1.5°/s、3°/s²等原日常默认值，已有调用兼容。本版把传入的同一组速度/加速度用于时间重规划和BEGIN报文上传，不会重规划用3、上传用5，也不会悄悄改成3。GUI折叠高级编辑区也不再覆盖用户显式设定的值。

固件协议接受最大120°/s²，不是最大3；这是软件数据范围，不是设备已验证的安全加速度。如果同事平台自己的输入框、配置文件或后端校验把最大值写为3，也要同步调整那层。该仓库不能替外部平台修改校验。

`max_accel`是上限，不是强制要求达到的加速度。原轨迹本来就低于3，改成5也可能看不到速度变化。已被放慢的点不会自动被压缩回原时间；请用原始轨迹点重新准备。共同减速还会根据实际误差继续放慢路径。不能用调大`max_error`代替查明误差来源；5°/s²也不是本版已实机验证的安全数值。

## 截图中故障7如何处理

俯仰误差1.031°超过0.75°，表示STM32轨迹跟随保护触发；驱动器报警0表示驱动器没有相应Err报警。单张截图不能证明是某个加速度数值导致，要结合故障前目标/实际角度、转速、实际周期以及驱动器加减速时间判断。

推荐流程：

1. 保存故障会话、错误码、两轴误差及实际角度日志。
2. `stop_trajectory()`停止两轴并等待零速，不能只停单轴后把平台故障标记清掉。
3. 检查反馈、参考、报警、限位和机械状态，降低或修正过快轨迹、解决通信异常。只是清故障不会消除故障原因。
4. 参考仍有效且当前条件正常时，调用`clear_trajectory_fault()`。它只确认取消故障任务，不运动、不复位驱动器、不清参考。
5. 实际位置可能在半途。确认返回路径安全后，使用`prepare_return_to_start(original_points)`预载返回路径，再明确启动并等待返回完成。恢复原轨迹要重新预载，不重播旧会话。

```python
fault = motors.get_trajectory_status()  # 调用方先保存这份快照
motors.stop_trajectory()
positions = motors.get_axis_positions()
print(fault.fault_text, positions)

# 已检查实际条件、处理故障原因后，显式确认：
motors.clear_trajectory_fault()

# 此处先由操作人员/业务逻辑确认整条返回路径安全：
back = motors.prepare_return_to_start(original_points)  # 只预载
motors.start_trajectory(back.session)
motors.wait_trajectory(back.session)

# 返回原业务首点后重新准备业务，不使用旧session：
ready = motors.prepare_business_trajectory(original_points, max_speed=0.5, max_accel=1)
# 需要执行时再start_trajectory(ready.session)
```

GUI主窗口新增“故障处理”入口，不要求电机1已经回到水平才允许查看/处理故障。轨迹窗口新增“确认清除轨迹故障（不运动）”；成功后核对实际位置，再准备回首点。不要用驱动器“复位报警”按钮清理轨迹故障，也不要重新置零掩盖当前位置。

通常的跟随误差故障7且参考有效时，不需要手动摆回+25°。如果掉电、参考无效、反馈单位不一致或通信故障使参考失效，清故障会拒绝，此时要先恢复通信并在真实姿态重新建立参考。驱动器Err报警、限位未解除或机械问题也需先处理相应原因。

## 清故障协议与限制

新增0x38，设备1，parameter必须匹配当前session，无请求数据；回复沿用40字节轨迹状态。只允许故障、取消、完成终态，拒绝运行、停止确认中、上传中或已预载任务。

固件独立读取两轴反馈并校验参考、范围（电机2按是否启用）、报警、保护、硬输入状态，间隔20ms再检查一次，两次均零速才清除。任何失败保留故障快照。成功后清空旧任务缓冲/会话并进入IDLE，不清参考、不写驱动器参数、不触发运动。迟到的旧START/心跳不能恢复任务。SDK会拒绝清除运行或预载任务；处于停止确认中的故障可等待组停稳后再清。

这不是“所有故障一键消除”的接口，底层报警/限位/参考问题不会被它绕过。旧固件的另一条正常路径是重新BEGIN一个新会话并预载；若平台把任何故障都在BEGIN之前永久拦住，就需要接入本确认清除流程。

## 验证边界

测试验证max_accel=5贯穿重规划、API及实际上传帧，折叠编辑器不覆盖；清故障验证双次零速、参考/报警不满足时拒绝、保留故障快照、成功不运动/不清参考、作废旧会话、旧固件不假成功。完成Python/C模拟测试、STM32编译及无硬件界面构造检查；尚未实机验证跟随性能、加速度5或故障恢复路径。
