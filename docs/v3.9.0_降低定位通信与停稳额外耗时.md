# v3.9.0：降低定位通信与停稳额外耗时

本版需要同时更新 H7 固件和上位机/SDK。固件适用于原 STM32H743 主网口板，TCP仍为 `192.168.10.50:5000`。不适用于未同步的 F407 备用工程。

## 本次解决的开销

用户10°往返截图中，设定1.5对应实际输出轴0.25rpm，即1.5°/秒。两个完整10°段分别8.203s、8.218s；相对各6.667s理想匀速时间，总差额约3.088s。差额包含加减速、末段逼近、通信和完成反馈，不能全算作可删除的软件等待。截图中每轴ACK约0.4～0.5s、两轴下发间隔约0.5s、到位窗口后约0.84～1.17s是优化线索，并非本版已经实测节省的数值。

用户HTML分析针对v3.8.6源码。当前v3.8.7已有板端完成标记及两轴直接反馈，本次在此基础上继续优化。HTML中的DAQ连续接收、异步落盘和叶片判定属于同事的采集平台，未在本仓库修改。

| 路径 | 修改 |
|---|---|
| 定位准备 | P3-0～5由六条单读合成一次连续读取；PA41/42合并读取。驱动不支持连续区间且返回Modbus异常时，回退逐项读取；通信超时不自动重试运动 |
| 再次定位 | 每次实读DI、实际控制模式、强制输入、速度来源及PA24。确认内部速度模式仍正确且PA24已清零时，复用当前模式，避免重复写配置。初次或配置变化仍走完整准备和读回检查 |
| 启动前停稳 | 首次状态读计入零速样本。前次定位已有两次零速完成证据时，一次新的零速及当前位置验证可复用证据；否则仍需两次独立读取。显式停止仍清除旧完成证据 |
| 运动中保护 | 点位控制每周期读取位置、速度、报警并执行软范围检查；单位P3-32/PA11至少每100ms尝试校验。Guard不再为同一个活动点位另读一遍状态和单位；硬件/双限位边沿和停机处理仍每次任务调用执行 |
| 控制调度 | 下一周期期限从本周期开始计时，替代“通信工作结束后再固定等50ms”。停稳阶段仍20ms；发生超时不追赶补发旧速度；制动预算仍使用实际反馈间隔 |
| 上位机查询 | 运动过程中复用年龄≤200ms的控制样本，减少强制直接查询争用总线；最终完成仍需直接来源、有效参考、无报警/故障、实际零速和板端完成证据 |
| 两轴提交 | 新0x1A命令一次提交两轴绝对目标，在两轴准备均成功前不执行点位速度任务。任一轴准备失败取消两轴，避免PC先等轴1 ACK再提交轴2 |
| 板端计时 | 0x1A应答返回每轴整段准备时间；新增0x1B读取最近点位初始化、控制工作时间及实际控制周期，便于区分PC观察延迟和固件耗时 |

两轴仍通过共享RS485依次读取和写入，不保证同一硬件时刻启动或同步到达。单包下发间隔为0表示同一个PC请求，不代表驱动器机械响应时间差为0。

没有提高实际速度、放宽终点容差或取消独立停稳确认。PA24速度更新仍保留写后读回核验，避免仅凭写应答认定实际设定已改变。起步约200ms分段限速、方向/不启动检查、通信故障与限位保护继续生效。

## 上位机测试

1. 烧录本版 `LightCheck.hex`，启动同一发布包里的 `app/start_simple.bat`，确认标题v3.9.0。
2. 建立电机1参考，建立或确认电机2参考，然后停止其他动作。
3. 主窗口进入「两轴联动往返计时」，保持与旧测试相同速度1.5、目标 `10,10 → 0,0 → 10,10`。每段两轴完成后才进入下一段。
4. 导出CSV。原表格各阶段均保留；日志新增 `JOINT_PREPARE_MS (轴1,轴2)`，单位ms，来自板端。
5. 完成后点击「读取板端耗时」，查看两轴初始化、控制工作、周期和最大周期；日志输出 `BOARD_TIMING`。它不发运动、不清参考。

未更新固件时新0x1A会被拒绝；上位机不会降级重发旧运动。先完成配套更新，再启动测试。

每轴“应答”包含两轴准备总过程及传输；“启动”是PC首次观察到非零速度，包含采样/传输延迟。各列有包含关系，不能全部相加。整段联动总耗时取两轴均完成时刻；已在目标的轴也通过新任务确认，显示无需运动。

本版尚无真实硬件对照结果，不能承诺节省几秒或达到某个总时长。请用相同负载、角距、速度和PA参数交错重复至少20次，比较p50/p90/max，以及过冲、反向停止和到位后抖动。不要仅凭ACK更快判断运动或采集已就绪。

## 同事/AI的SDK接入

`move_axes_to`的速度是真实输出轴rpm，**不除以6**。只有GUI复位/联动测试框的设定值以及已有高级复位API沿用÷6规则。

```python
from app import MotorController

with MotorController('tcp://192.168.10.50:5000',
                     timing_log='logs/motion_timing.jsonl') as motor:
    # 调用前两轴必须已建立参考且停稳；本段不会自动回零或重设坐标。
    for targets in ((10, 10), (0, 0), (10, 10)):
        accepted = motor.move_axes_to(targets, speed_rpm=0.25)
        print('板端整段准备ms:', accepted['board_prepare_ms'])
        motor.wait_for_axes(targets, tolerance_deg=0.1, timeout_s=120)
    print('最近点位板端耗时ms:', motor.get_point_timing())
```

`move_axes_to(targets_deg, *, speed_rpm=0.1)`：两个绝对参考角度，共用一个真实输出轴速度；ACK仅代表两轴已准备。要求两轴有参考、无故障且无运行任务。不得用它直接替换活动点位；先停止并确认停稳。已有单轴0x19换向流程保持兼容。函数不进行额外PC侧预检/停止/重新建立参考；校验由同一个板端操作完成。

`wait_for_axes`仍核验两轴位置、参考、报警、故障、零速和完成状态。运动中使用共享反馈，候选完成会要求直接反馈；有板端两次零速证明时无需PC再重复两轮。未获得板端完成标记时，保留两轮直接零速判断。

`get_point_timing()`返回两轴字典组成的tuple，字段单位均为ms：

| 字段 | 含义 |
|---|---|
| init_ms | 最近一次start_point内部准备耗时；不包含外层坐标读取和预检，因此小于等于0x1A对应轴整段准备时间 |
| cycle_work_ms | 最近一个成功控制周期的工作耗时，包含阻塞读写，不含调度等待 |
| cycle_period_ms | 最近两次控制周期开始时刻之差 |
| max_cycle_period_ms | 本次点位中观测到的最大周期，重新提交任务时清零 |

0值可能表示本次尚未形成相应样本；故障中断的周期不更新成功周期工作值。它们是诊断数据，不是位置/停稳证明，也不是新增的配置项。

通信结果不确定时停止请求仍尽力向两轴发送；发送成功不代表已停稳，不自动重发定位。参考失效或保护错误按原有接口处理，不自动清故障。

## 协议

沿用 `AA 55 / Length / Device / Command / Parameter / Data / CRC16`。

- `0x1A / Device=1 / Parameter=0x4A50 (JP)`：数据10字节，`>Hii`，真实输出轴0.01rpm、轴1绝对毫度、轴2绝对毫度；成功应答8字节 `>II` 为各轴整段准备ms。两轴均准备好后才允许点位任务运行。出错不得自动重发或降级。
- `0x1B / Device=1 / Parameter=0x544D (TM)`：无数据，成功应答32字节 `>8I`，先轴1四字段再轴2四字段，顺序同上表；不为查询额外读取驱动寄存器。常规保护/控制任务仍照常调度。
- `0x37 / Parameter=0`：可返回年龄标记的共享控制样本；`source=1`不能冒充直接完成证据。`Parameter=0x4652`仍强制实读两轴。
- 原有单轴0x19、0x14及其他API保留兼容；需要性能收益的同事应更新SDK并采用新双轴提交/组合等待，而非继续在调用端重复预检、停止和全量读取。
